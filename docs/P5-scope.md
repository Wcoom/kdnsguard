# P5 范围（缩小后）

日期：2026-10-05。依据：用户在 2026-10-05 对本方案「安卓私人 DNS 状态桥」的澄清。

---

## 0. 澄清改变了什么

方案 §10 的标题是「安卓私人 DNS 对齐：使用系统接口，不伪造安全状态」，
§10.2 列出了四条适配器职责（读 netId/VPN/private-DNS 状态、提交查询、
回报状态给 DnsResolver/ConnectivityService、处理网络事件），
§10.1 的第二种模式还要求把 off/automatic/hostname 的系统定义语义搬进内核。
一句话概括原文：**把内核 DNS 桥接进安卓的私人 DNS 状态机**。

用户澄清的是：**§10 说的「私人 DNS 状态桥」指的是「内核态 DNS 的*效果*与
设置里的私人 DNS *一致*」，不是去兼容或桥接安卓的私人 DNS 设置与状态。**

这个区别是实质性的，不是措辞：

| | 原文读法（桥接） | 澄清后的读法（效果一致） |
|---|---|---|
| 谁拥有「私人 DNS 模式」 | 内核要实现 off/automatic/strict 三态语义 | **内核本来就只有一种模式**：单一上游 DoH、证书验证、零明文回落 |
| 需要什么材料 | AOSP DnsResolver / Resolver APEX 源码、签名、权限 | **不需要** |
| 需要什么接口 | 双向状态桥（内核 → ConnectivityService 回报验证状态） | **不需要** |
| 失败条件 | 「拿不到 ROM/APEX 材料就阻塞」 | 阻塞项消失 |

**内核侧的严格模式与安卓私人 DNS 的 strict 在效果上是同一件事**：都保证
「解析结果只能来自一个经过证书验证的加密上游，绝不静默回落到明文」。
既然如此，就不存在「把三态语义搬进内核」的必要 —— 内核只有那一种行为，
而系统的三态是*系统*的事。

⇒ **P5 不再需要 AOSP `DnsResolver`/APEX 的状态桥，也不再需要把
off/automatic/strict 语义搬进内核。** 方案 §10.2 的四条职责里，
只有第 1 条（取 netId）与第 4 条（网络事件 → 事务）残留为工程项，
其余两条随澄清作废。§10.3 则从一个「无法解决的问题」变成一个
**可测的配置约束**（见 §2）。

## 1. P5 剩下什么

### 1.1 非 root 访问 `/dev/kdnsguard`（工程项，唯一真正必需的）

现状：字符设备靠手动 `mknod /dev/kdnsguard c 440 0` 创建，且 open 要求
`CAP_NET_ADMIN`。原因在 `kdg_chardev.c` 里写着：Android 的 `/dev` 是
**tmpfs 而非 devtmpfs**，`device_create()` 建不出节点。

要做的是最小权限路径，而不是放开权限：

- ueventd 规则（或等价机制）负责创建节点并设定属主/属组；
- open 的准入从 `capable(CAP_NET_ADMIN)` 收紧到「属于某个专用组 + SELinux
  策略放行」，让受信的系统组件能用，普通 App 不能用；
- SELinux 保持 enforcing，只加最小 `allow`。

⚠️ 这条不是「顺手做掉」的：它同时决定 P3 的接管在真实 ROM 上能否**无人值守
地**启用（现在每次重启都要手动 mknod）。

### 1.2 网络事件 → ownership 事务（工程项）

方案 §10.2 第 1/4 条：netId、VPN 状态、网络切换。现状是 `net_id` 恒为 0、
`network_epoch` 只有 genl 能写。

要做的：把「网络变了」变成一次明确的 PREPARE/COMMIT/DISABLE 序列，
而不是让内核猜。这与 P4 的多网络隔离（`kdg_pool` 目前仍是单连接、`init_net`）
是同一件事的两个面。

### 1.3 常驻交付形态（工程项）

模块是树外 LKM，而设备常规交付走 AnyKernel3（`do.modules=0` 只换 boot 内核段、
不装模块）。要常驻设备须改内建集成。这条此前记在「未决事项」里，归属 P5。

### 1.4 明确**不做**的

- 不匹配/替换 AOSP `DnsResolver`、不开 Resolver APEX；
- 不把 off/automatic/strict 做成内核态状态机；
- 不做「内核 → ConnectivityService」的状态回报；
- **不伪造「strict 成功」**。方案 §10.2 末段与 §10.3 的红线原样保留：
  没有系统集成时，只能交付「明文全局 DNS 接管 + 接口服务」，
  不得通过伪造证书或绕过平台验证去让设置页显示成功。

## 2. 由此推出的一条可测配置约束

**安卓私人 DNS 必须保持 `off`。**

理由在方案 §10.3：私人 DNS 的 strict 模式走 **853 端口**，而 §10.3 已经说明
内核**不能**接管 853 —— 客户端期望的是「原 hostname 的有效服务器证书」，
把它 NAT 到一个不同 hostname 的本地服务，证书验证必然失败。

所以如果系统自己开了 strict，它就会**绕过内核**去连 853：那是**两套解析器
并存**，不是「效果一致」。此时「与私人 DNS 一致」这句话就不成立了 ——
而且方向相反：内核在 53 上强制单一 DoH，系统在 853 上另连一个上游。

这条约束是可测的，应当成为 P5 的验收项之一：

| 检查 | 判据 |
|---|---|
| 私人 DNS 模式 | `settings get global private_dns_mode` 为 `off` |
| 无 853 外发 | 内核侧统计 853 端口的新连接数为 0（若将来加这个计数器） |
| 内核侧状态如实上报 | `kdgctl` 的 `private_dns_mode` 字段报告**观测到的**系统值，而不是假设它是 off |

⚠️ 最后一行是有意的：`kdg_cfg.private_dns_mode` 现在由 genl 下发，属于
「被告诉的值」。P5 应当让它反映**观测**结果，否则这条约束无法自动发现违反。

## 3. 与其它阶段的关系

- P5 **不阻塞** P6/P7：澄清之后 P5 已经没有「拿不到 ROM 材料」这堵墙，
  剩下的都是可以在本机开发、在真机验证的工程项。
- P4 的多网络隔离与 P5 的 §1.2 是同一件事，先做哪边都行，但要一次做完 ——
  分成两次会在 `kdg_pool` 里留下「连接按 netId 分，但事务不按 netId 走」的
  中间态。
- 方案 §16 的 P5 通过条件「off/automatic/strict、验证状态、VPN 语义明确且
  测试通过」需要按本文重写为：「非 root 可用、网络事件驱动事务、
  私人 DNS 保持 off 且内核如实上报、SELinux enforcing 下可用」。
