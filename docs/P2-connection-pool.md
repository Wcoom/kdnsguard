# 上游 DoH 持久连接池（方案 §6.3）

日期：2026-10-05。改动分支：`kdg/p3-kernel-listener`。

这一轮只有一个目标：**把 TCP+TLS 握手从「每次查询」降到「每条连接一次」**。

它不是一次优化，而是补一块此前被说成「已完成」的东西。P2 的验收表里写着
「H2 上游」，README 里也承认「尚未完成持久连接多流」—— 但直到 P6 第一轮把
代价量化出来（[`P6-measurements.md`](P6-measurements.md)），才看得清那句话
意味着什么：并发 64 时 p50 **14 秒**、159 条查询跑 **77 秒**、随机 1000 条
的 CPU 是用户态基线的 **707 倍**，而这些几乎全花在握手（密码学 + 多个往返）上，
与解析本身无关。

---

## 1. 改动形状：从「一把锁」到「一个驱动线程 + 一个队列」

旧实现的并发模型是把方案里的「单一执行者」**直译成一把模块级互斥锁**，
罩住从建连到关连接的整条查询。那是「正确但退化」的版本：H2 最值钱的
多路复用完全没被用上，因为每个查询都独占一条连接。

新实现按方案原文的模型重做：

```
调用方（字符设备 write / listener kthread）
   │  只做三件事：取槽、入队、等自己的完成
   ▼
[ g_pool.lock 保护的槽位表 + pending 链 ]
   │
   ▼
驱动线程（唯一触碰 socket / mbedTLS / nghttp2 的线程）
   建连 → 提交队列里的流 → read/mem_recv/send 循环 → 结算
```

**关键收益不是「快一点」，而是调用方不再阻塞在协议栈上**：握手、收包、重传
全在驱动线程里，调用方只是睡在自己的 completion 上。于是并发 64 与并发 1
对驱动线程没有区别 —— 64 条流在同一条连接上并行。

### 文件划分

| 文件 | 职责 |
|---|---|
| `kernel/kdg_upstream.{h,c}` | **一条**连接：TCP + TLS 握手 + ALPN + H2 会话。一个不透明句柄 |
| `kernel/kdg_h2.{h,c}` | H2 **会话**（不是「一次请求」）：建会话、提交多条流、喂字节、刷帧、释放 |
| `kernel/kdg_h2stream.h` | 单条流的收集状态。**只依赖 kdg_base.h** |
| `kernel/kdg_pool.{h,c}` | 策略：槽位、排队、超期取消、空闲关闭、谁在等谁 |
| `kernel/kdg_doh.c` | 传输选择：H2 走池，ALPN 非 h2 时回落 H1 兼容路径（§6.4） |

这层划分不只是整洁：把 `kdg_upstream` 分出去之后，`kdg_pool.c`
**不再依赖 mbedTLS 与 nghttp2**，因此可以在宿主上用 gcc + ASan 跑并发测试
（见 §5）。而并发正确性正是池层全部的风险所在。

## 2. 槽位生命周期：两条靠结构消除的隐患

`struct kdg_pool_req` 是调用方与驱动线程之间**唯一**的共享对象：

```
FREE ──调用方 alloc──▶ ALLOC ──调用方入队──▶ QUEUED ──驱动 pump──▶ INFLIGHT
                                               │                      │
                                               └──────── 终态 ────────┘
                                                            ▼
                                                          DONE ──▶ FREE
```

两条容易写错的地方，用结构本身而不是注释来消除：

### 2.1 `INFLIGHT → DONE` 要求 `st.done && !st.in_flight`

`in_flight` **只由协议栈的 `on_stream_close` 回调清掉**（或整个会话被销毁时）。
也就是说「协议栈已经彻底忘掉这条流」是归还槽位的前提。

为什么这是硬要求：END_STREAM 只说明*响应收齐了*，而 nghttp2 紧接着还会在
`on_stream_close` 里写同一个收集结构。若在 END_STREAM 就交付槽位，调用方会立刻
把它还给池、下一条请求 `memset` 复用同一块内存，而旧流的 `on_stream_close`
随后写进新请求的字段 —— **串台**。

> ⚠️ 多数情况下这两个回调发生在同一次 `mem_recv` 内，所以「不写这条判断」
> 在真机上要撞运气才出问题。宿主测试里为此专门让替身**把两件事分成两次调用**，
> 否则这条不变量根本测不到（实测：合并成一步时，把判断删掉的注入是全绿的）。

### 2.2 谁释放谁

- 正常路径：调用方读完结果自己归还；
- 调用方超时离开的槽位带 `abandoned` 标记，由驱动线程负责取消、收尾与归还。

两边都只在 `g_pool.lock` 里改 `abandoned`，所以既不会双重释放也不会泄漏。
**调用方超时后绝不自己释放** —— 协议栈可能还持有它的指针。

而「调用方超时」这条路本身**正常运行时走不到**：驱动线程的超期扫描会在
deadline 内结算每一个槽位。它存在是为了让「池实现出错」退化成一次可诊断的
`-ETIMEDOUT` + 一条 `wait_timeouts` 计数，而不是一个挂死的进程。

## 3. 三条与方案原文的对应

| 方案 §6.3 原文 | 落点 |
|---|---|
| 「每网络一条按需连接」 | 连接懒建立（第一次查询），此后复用；身份变化即重建 |
| 「32 个活跃流，按对端 SETTINGS 可增至 64」 | `KDG_UPSTREAM_STREAMS_INIT/MAX`；**必须区分「对端声明了 100」与「对端还什么都没说」**——nghttp2 把未声明的 max_concurrent_streams 预置成 RFC 默认 100 |
| 「空闲连接 60–180 秒关闭、无保活」 | `KDG_POOL_IDLE_MS = 90000`（区间中点）；连接关闭后驱动线程**无限期睡眠**，方案 §9.3 的「无请求时 worker 睡眠」由此成立 |

### 读滴答（`KDG_UPSTREAM_TICK_MS = 250`）是这份实现唯一新增的机制

驱动线程既是收包的、也是出队的：它得定期回来提交新入队的请求、取消超期的流。
若一次读阻塞整个 deadline，这三秒里上面两件事都做不了。所以把 socket 的
**接收**超时设为 250 ms 的「滴答」，并在 `kdg_sock` 层把它与**发送**超时拆开
（`kdg_sock_set_rcv_timeout`）—— 前者是「多久回来扫一遍」，后者是「写不出去
就是这台上游不可用」，绑成一个值要么让取消变迟钝、要么让慢一点的写被判死。

配套改动在 `kdg_tls.c`：**接收超时不是错误，是 `MBEDTLS_ERR_SSL_WANT_READ`**。
这是 mbedTLS 的标准非阻塞约定（`ssl_msg.c` 把 bio 的负返回原样上抛，且
`in_left` 保留半个记录的进度，因此返回 `-EAGAIN` 不丢数据）。若在 bio 里把
超时报成 `RECV_FAILED`，一条完全健康的空闲连接会每 250 ms 被判死一次。

## 4. TLS 共享状态的锁粒度收细

旧的 `kdg_tls_lock()` 罩住整条查询，副作用是 DRBG 天然不会被并发访问。
连接长期存在之后那把粗锁不能再罩整条查询（等于放弃池化的并发性），
于是按 `kdg_tls.h` 里早就写下的话把粒度收到两处：

- **DRBG**：`kdg_tls_rng()` 包装，只在取随机数时持锁；
- **信任锚链**：只在任何一次握手期间持锁（与 `add_ca`/`clear_ca` 互斥）。

H1 兼容路径的持锁范围也随之从「整条查询」缩到「只罩握手」。

## 5. 验证：宿主并发测试 + 反向注入

新增 `tests/test_pool.c`：**直接编译 `kernel/kdg_pool.c` 原文**（不是副本），
依靠 `tests/hostlinux/` 的一组 `<linux/*.h>` 替身跑在宿主 gcc + ASan/UBSan +
真 pthread 上。`kdg_upstream_*` 被换成一个可编排的替身。

11 个用例、447 项检查，覆盖：单次往返、顺序 200 次只建一条连接、并发 64、
上游不响应时的超期取消、调用方放弃、连接级失败、H1 回落抑制、槽位打满、
上游身份变化、空闲关闭、卸载时仍有等待者。

### 5.1 反向注入：证明这些用例不是空闸

```
python3 tests/inject_pool_defects.py
```

**正向全绿不构成证据** —— 只说明「它没拦你」。这个脚本给 `kdg_pool.c` 注入
已知缺陷，要求每条都被抓住：

| 注入的缺陷 | 结果 |
|---|---|
| 放弃路径自己释放槽位（双重释放/UAF） | ✅ 抓住（LeakSanitizer + slots_used） |
| 结算时不要求 `in_flight` 已清（串台） | ✅ 抓住（reuse_while_live） |
| 没有装载闸门（卸载后仍受理） | ✅ 抓住（返回 -EINVAL 而非 -ESHUTDOWN） |
| 驱动线程不结算（调用方只能等自己的上限） | ✅ 抓住（耗时 2400ms 而非 400ms） |
| 超期不取消在途流（不发 RST） | ✅ 抓住（stream_resets_sent） |
| 槽位不归还（每次放弃漏一个） | ✅ 抓住（slots_used + LeakSanitizer） |
| 调用方自己拆连接（换上游时的 use-after-free） | ✅ 抓住（ASan heap-use-after-free） |
| 归还时忽略 `in_flight` | ⚠️ 非闸门：该判断当前**可证明不可达**（见下） |
| 卸载不等调用方离场 | ⚠️ 非闸门：与调度顺序赛跑，注入后时红时绿 |

两条 ⚠️ 如实记录而不是删掉：
- **「归还时忽略 in_flight」**：`free_slot` 只在 ALLOC/DONE 两态被调用，而
  DONE 的两条入口都已经各自保证过 `!in_flight`。所以它是**记录不变量的
  防御性断言**，不是执行分支 —— 删掉它测不出差别是正常的。真正的防线在
  `settle` 与 `fail_all` 里，那两条都有确定性用例。
- **「卸载不等调用方离场」**：调用方能否在 `kvfree` 之前写完它那一次写入，
  取决于两个线程谁先拿到 `g_pool.lock`。要确定性复现得往产品代码里插延时，
  那比留一个已知缺口更糟。

### 5.2 评审与测试各自抓到的东西

**先说清楚覆盖边界**：宿主测试跑的是池层的状态机，**协议栈那一侧
（mbedTLS / nghttp2 / socket）在这里是替身**。因此下面两个真实缺陷里，
一个是测试抓的、一个是**读代码抓的** —— 分清这一点比记住缺陷本身更重要，
它标出了「这套用例能替你挡住什么」。

#### 由测试抓到的（ASan 当场终止）

**换上游时的 use-after-free。** 拆连接原本写在 `kdg_pool_check_identity_locked()`，
而那个函数跑在**调用方线程**上；驱动线程可能正阻塞在一次
`kdg_upstream_read()` 里 —— 那一段**不持 `g_pool.lock`**（读要阻塞到有数据，
不能占着锁）。调用方此时 `kdg_upstream_close()`，就是把驱动线程脚下那个
mbedTLS/nghttp2/socket 对象 free 掉，而它手里还攥着指针。

修法不是加锁，而是**把拆连接的权限收归驱动线程**：调用方只留下一个
`rebuild` 待办，驱动线程在下一轮循环开头执行。测试
`test_identity_change_during_read` 用一个「让驱动线程卡在读里」的替身旋钮
把这件事变成确定性的，注入原实现后 ASan 给出
`heap-use-after-free ... in kdg_upstream_read`。

#### 由读代码抓到的（测试看不见，因为那部分被替身掉了）

**TLS 锁自死锁。** 把 DRBG 的保护从「整条查询一把锁」收细到
`kdg_tls_rng()` 之后，最初的写法是让它复用 `kdg_tls_mutex` —— 而
`mbedtls_ssl_handshake()` 内部就会调 `f_rng`，调用方**已经持有那把锁**。
结果是**第一次握手就自死锁**：症状是「第一次查询永久挂住、日志里什么都没有」。

修法是**两把锁**：`kdg_tls_mutex` 保护信任锚链（整段握手期间持有），
`kdg_rng_mutex` 只保护 DRBG（一次取随机数期间持有），两者之间没有反向获取。

> 这一条**测试抓不到** —— `kdg_upstream` 在宿主测试里是替身，mbedTLS 根本
> 不在场。它提醒的是：这套用例的价值边界恰好是「协议栈之外的那部分池逻辑」。

#### 顺带记下的三条工程教训

写这份测试的过程本身还产出了三条值得记的东西：

1. **替身必须模拟真实对象销毁时的后果，不能只模拟它的接口。**
   `kdg_upstream_close` 最初只 `free(u)`，而真实现里它调
   `nghttp2_session_del()`，此后 nghttp2 不可能再拿任何旧的 `stream_user_data`
   回调 —— 池正是靠这个才敢在连接级失败路径上自己清 `in_flight`、立刻复用槽位。
   替身没模拟这一后果，于是在重连后的复用发生时**报出假故障**（8 次里红 7 次）。
   同理，替身的阻塞读**必须解引用那个连接对象**，否则「调用方趁读把它 free 掉」
   这类 UAF 在宿主上永远看不见 —— 不碰这个对象，就没资格声称测过这个对象。
2. **`nanosleep` 的 `tv_nsec` 必须 < 10⁹。** `(struct timespec){0, 1200 * 1000000L}`
   直接返回 `EINVAL` —— 「阻塞 1.2 秒」变成「立刻返回」，测试还在跑、却已经
   什么都没验到。放弃路径的用例因此一直没走到它该走的分支。
3. **一块反复初始化的静态对象会让「登记表」变成自环。** 宿主替身用一个链表登记
   所有 waitqueue 以便广播唤醒；`kdg_pool_init` 每次都会 `init_waitqueue_head`
   同一个静态 wq，第二次就把 `wq->next` 指回它自己，遍历永不终止 —— 症状是
   「线程函数明明已经返回、`pthread_join` 却永不返回」。改成定长数组 + 指针去重。

## 6. 协议层的两处顺手修正

- **接收窗口**：HTTP/2 的连接级接收窗口默认只有 65535 字节，而 64 条 4 KiB 的
  DNS 响应合计 256 KiB。默认值下服务端发满 64 KiB 就停下等我们的 WINDOW_UPDATE
  —— 功能正确，但白白多出几个往返。已把连接窗口提到 1 MiB、并在 SETTINGS 里
  声明每流窗口 256 KiB（窗口是记账，不预分配内存）。
- **GOAWAY 的处理是保守的**：收到即视为会话不可再用，在途流一并失败。
  按 RFC 9113 §6.8 本可以只失败 `> last_stream_id` 的那些，但为一个单上游
  DoH 端点维护「排空状态机」不划算。注意结算发生在 GOAWAY 判定**之前**，
  所以「服务端把最后几条响应和 GOAWAY 发在同一批」这种情况不会丢结果。

## 7. 真机验证（P6 第二轮，2026-10-05）

**已真机验证**，详见 [`P6-round2.md`](P6-round2.md)。结论比预期彻底：

| | 第一轮 | 第二轮 |
|---|---|---|
| 冷查询并发 64 wall | 77.0 s | **0.459 s（短 168×）** |
| 冷查询并发 64 p50 | 14161 ms | **86.8 ms（快 163×）** |
| 随机 1000 wall | 207 s | **6.82 s（短 30×）** |
| 随机 1000 调用方 CPU | 22615 ms | **133 ms（低 170×）** |
| `pool_connects : doh_queries` | 1 : 1 | **1 : 1000** |
| 并发方向 | c64 比 c1 慢 2.6× | c64 比 c1 快 31.5× |

方案 §6.3 的三条逐字达标也在真机上量到了：并发流上限 32（对端 SETTINGS 前）
→ 64（之后）；空闲 95 秒后连接被主动关闭、再查一次重建；零告警、`rmmod` 干净。

### 仍然没验证的
- **真实的慢上游 / 弱网**。宿主替身里的「不响应」「连接级失败」是布尔开关，
  不是真实的丢包与重传。
- **netId / fwmark 多网络**。池仍是单连接、`init_net`，方案 §5.3 的多网络
  隔离属于 P4/P5。
- **能耗**。见 `P6-measurements.md` §0：本装置测不了，红线不变。

## 8. 预期 vs 实测

那一节的四条**假设**，现在有了数字（完整表格见 `P6-round2.md`）：

| 当时的预期 | 实测 |
|---|---|
| 冷查询 p50 从秒级降到与上游 RTT 同量级 | ✅ 14161 ms → 86.8 ms（上游 RTT 量级是 50–70 ms） |
| 每查询 CPU 从 31 ms 降到接近零 | ✅ 调用方 CPU 22615 ms → 133 ms（1000 条随机域名） |
| `pool_connects : queries` 从 ~1:1 变成 ~1:N | ✅ **1 : 1000** |
| 并发不再退化成队列长度 | ✅ c64 从「比 c1 慢 2.6×」变成「比 c1 快 31.5×」 |

但**没有变成零差距**：内核的 wall 仍是 mihomo 基线的 1.45–2.25×，p50 高约 40 ms，
合计 CPU 高一截。这些差距的成因尚未定位，如实记在 `P6-round2.md` §3。
""
