# P6：DNS 性能与机制量测量（第一轮）

日期：2026-10-05。设备：OnePlus 13 / PJZ110。依据：方案 §17.3（性能）、§17.4（能耗）。

工具：`clients/rust/kdg-client/examples/kdgbench.rs`（零依赖，交叉编译到
aarch64-linux-android）；轨迹在 `clients/rust/traces/`。

---

## 0. 先说清楚这轮**测不了什么**

### 🔴 能耗（mJ/有效查询）在本装置下**不可测**

方案 §17.4 要求「优先用外部功率仪，不能只从电量百分比推导毫焦」。本轮的硬约束：

| 条件 | 实测 |
|---|---|
| 外部功率仪 | **没有** |
| 设备上唯一可用的仪器 | 电量计 IC：`/sys/class/power_supply/battery/{current_now,voltage_now}` |
| 充电状态 | **`status=Charging`，`current_now=0`** —— 手机正通过 USB 充电（也是 adb 通路） |
| 能否断开充电测量 | ❌ 断开 USB 就同时断开 adb（唯一控制通道），而笔记本的网络本身还依赖这条 USB 共享；`adb tcpip` 走 Wi-Fi 也不成立——笔记本此刻没有别的网络 |

充电电流把 DNS 层面的任何差异都掩掉了。**所以本轮不给任何 mJ 数字**，也不说
「更省电/更费电」。方案 §17.4 自己立的红线是「差异在测量噪声内不宣传更低能耗」，
这里比噪声更根本：**根本没有可用的功率测量**。

要做真正的能耗结论，需要二者之一：
1. 外部功率仪（最好带采样输出）；
2. 控制通道与充电解耦（例如手机走 Wi-Fi 共享、adb over TCP，USB 只充电或完全不插），
   然后用 `current_now × voltage_now` 积分——**且必须做空载对照并报噪声底**。

### 其余可测的量（本轮交付）

延迟分位数、CPU 时间（`CLOCK_PROCESS_CPUTIME_ID`，纳秒精度）、上下文切换、
物理出口的包数/字节数（radio tail 的**代理量**，不是能耗）、以及内核侧的
缓存/同名合并/上游计数。

## 1. 两条被测路径

| 标签 | 路径 | 说明 |
|---|---|---|
| **A** 基线 | UDP → `127.0.0.1:1053` | mihomo 用户态 DNS（方案 §17.4 的 A 组） |
| **C** 内核 | `/dev/kdnsguard` 字符设备 | 本项目（方案 §17.4 的 C 组） |

两条路径都走同一个上游 DoH、同一网络、同一轨迹。内核路径每档都**重新
`rmmod`+`insmod`** 以获得真空缓存；基线的「冷」用 `boxctl service restart` 冷掉
它的 DNS 缓存（两侧的缓存状态因此都受控）。

## 2. 结果

轨迹全部用**提交版** `clients/rust/traces/real.txt`（159 个不同真实域名），
`burst100.txt`、`random1000.txt` 同。

### 2.1 延迟、CPU、wall（冷查询 / 热查询，两种并发）

**⚠️ 口径**：A 的「冷」是 `boxctl service restart` 后立刻跑（它的 DNS 缓存冷、
连接池也冷）；C 的「冷」是 `rmmod`+`insmod` 后立刻跑（缓存真空）。**两者都是冷**，
不是拿一方的冷去比另一方的热。

### 2.2 缓存命中率与同名合并（内核侧精确计数）

| 场景 | resolve_cache | resolve_upstream | resolve_joined |
|---|---:|---:|---:|
| 冷 159 条（c1/c16/c64） | 0 | 159 | 0 |
| 热 159 条（c1） | 150 | +9 | 0 |
| 热 159 条（c16） | 113 | +46 | 0 |
| 热 159 条（c64） | 87 | +77 | 0 |
| **同名爆发 100 条（c32）** | 68 | **1** | 31 |

两点值得单独记：

- **同名爆发逐字达标**：100 次同名并发 → 上游 **1** 次，31 条搭车、68 条命中缓存。
  这正是方案 §17.3 的验收口径。
- **热查询的命中率随并发下降**（150 → 113 → 87）。原因是冷查询本身在并发下拖得很长
  （c64 达 77 秒），而轨迹里有相当一部分域名的 TTL 是几十秒级 ——
  等冷查询跑完再跑热查询时，**一部分条目已经过期了**。这不是缓存实现的问题，
  是「冷查询太慢」的连带效应。

## 4. 由测量直接导出的下一步（优先级最高）

**实现方案 §6.3 的 H2 持久连接池**：每网络一条按需 TCP+TLS 连接、32 个活跃流
（按对端 SETTINGS 可增至 64）、空闲连接 60–180 秒关闭、无保活。

预期效果（可验证的假设，不是承诺）：
- 每查询 CPU 从 31 ms 降到接近零（握手是 CPU 大头，这是本轮最硬的证据）；
- 每查询的握手包数归零（省掉每次 TCP 三次握手 + TLS 握手往返）；
  ⚠️ 修好之后窗口会从 38 秒降到 1 秒量级，**那时包数才第一次变得可测**
  （见 §2.3）——所以这个指标要等 §4 做完再回来测；
- 冷查询 p50 从秒级降到与上游 RTT 同量级；
- 并发度不再退化成队列长度（流可并行）。

**这就是 P6 最大的产出**：它把「P2 已完成」这句话里**没完成的那一块**定位出来并
量化了代价——此前 README 只承认「尚未完成持久连接多流」，没有数字说明那意味着
什么。

## 5. 本轮未覆盖

1. **能耗**（见 §0）。
2. **10 万级查询轨迹**：方案 §17.3 要求 100/1000/10000 三档。本轮跑到 1000
   （`random1000.txt`），且内核侧 1000 条随机域名要跑 **192 秒**——在上游连接池
   修好之前，上更大规模只是让噪声更大，没有信息增益。
3. **Wi-Fi 与蜂窝分别测**：本轮全部在蜂窝（`rmnet_data3`）。注意本轮期间设备
   网络换过一次接口（`rmnet_data5` → `rmnet_data3`），接口名不能写死。
4. **热点/共享网络路径**的延迟与包数。
5. **休眠/唤醒**：`debugfs` 未挂载，`wakeup_sources` 不可得；本轮**没有**为测量
   去挂 debugfs（上一轮已有"为不好用的指标扩大宿主暴露面不划算"的教训）。
   方案 §9.3 的「无请求时 worker 睡眠、无周期网络包」需要在可观测唤醒源的装置上验。
